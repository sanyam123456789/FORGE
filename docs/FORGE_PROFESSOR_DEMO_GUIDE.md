## Section 1 — Project Title and One-Line Explanation

**Title:**

```text
FORGE — An AI Coding-Agent Harness for Controlled Evaluation
```

**One-line explanation (for the professor):**

FORGE is a lightweight, instrumented coding-agent harness that runs an LLM
against real coding tasks through a controlled tool-and-file-execution loop,
and records detailed metrics (tokens, calls, latency, success) so that
different agent strategies can be compared scientifically instead of
anecdotally.

## Section 2 — Problem Statement

**What problem FORGE addresses**

Modern coding assistants are usually evaluated informally — a person asks a
chatbot to write code and judges the result by eye. This does not produce
comparable, repeatable numbers, and it hides how much the harness itself
(how tools are exposed, how conversation history is managed) affects cost
and performance versus the underlying model. FORGE exists to isolate and
measure that harness layer.

**Why ordinary LLM chat is not enough**

A chat interface does not execute tools, does not touch a real filesystem,
does not enforce turn/call limits, and does not record structured metrics.
It cannot answer questions like "how many tool calls did it take?" or "how
many tokens were spent on context repeated across turns?" — because it
does not track any of that.

**Why repeatable tasks, tool execution, isolated workspaces, and metrics are needed**

- **Repeatable tasks** (`experiments/tasks/`) let the same coding problem be
  given to different configurations, so results are comparable rather than
  one-off.
- **Real tool execution** (`read_file`, `write_file`, `edit_file`,
  `list_directory`, `run_shell`) means the agent produces actual files, not
  just text — closer to how a coding agent is really used.
- **Isolated workspaces** prevent one run's file changes from contaminating
  another run or the FORGE source tree itself, which is required for a fair
  comparison.
- **Metrics** (tokens, LLM calls, tool calls, latency, context size) turn
  "the agent worked" into numbers that can be compared across
  configurations.

**What FORGE is trying to measure**

Per `README.md` and `docs/architecture.md`, FORGE's research question is:

> Can a coding agent achieve comparable software-engineering task
> performance with **lower token usage, cost, latency, and context
> consumption** through **adaptive tool exposure** and
> **interaction-context management**?

## Section 3 — Main Workflow

Verified against `forge/agent.py` (`AgentRuntime.run()`) and
`docs/architecture.md` §"Agent Loop":

```text
User gives a coding task
        ↓
FORGE CLI receives the task            (forge/cli.py)
        ↓
Agent builds context (system prompt + task)   (forge.context)
        ↓
Agent sends the context + exposed tool schemas to the LLM   (forge.llm)
        ↓
LLM decides whether it needs to call a tool
        ↓
If yes: tools read/create/edit files or run a shell command  (forge.builtin_tools, guarded by forge.safety)
        ↓
Tool result is appended to the conversation and the loop repeats
        ↓
When the LLM responds with no further tool calls, that text is the final answer
        ↓
Generated files remain in the workspace the run was pointed at
        ↓
Metrics and a JSONL trace are recorded for the whole run   (forge.observability)
```

**Per-step explanation**

1. **User gives a coding task** — a natural-language instruction, e.g. "Create
   a file named hello.py containing a function greet(name)...".
2. **FORGE CLI receives the task** — `forge run --task "..."` parses the
   request and loads configuration (`forge.config.load_settings()`).
3. **Agent builds context** — `ConversationContext` starts as the system
   prompt (`forge.prompts.FORGE_SYSTEM_PROMPT`) plus the user task.
4. **Agent sends the task to the LLM** — `LLMProvider.complete(messages,
   tools=...)`; which tools are exposed is decided by the
   `ToolExposureStrategy` (Fixed or Adaptive).
5. **LLM decides which tools are needed** — the model's response either
   contains tool calls or a final text answer.
6. **Tools read/create/edit files** — each tool call is validated and
   dispatched through `ToolRegistry`, and every filesystem/shell operation
   is checked by `forge.safety` (workspace boundary, overwrite guard,
   command blocklist) before it runs.
7. **Agent continues until task completion** — tool results are appended as
   messages and the loop repeats, bounded by `max_llm_turns` and
   `max_tool_calls`.
8. **Generated files are saved in a workspace** — all file operations are
   confined to the configured `--workspace` root.
9. **Metrics and trace are recorded** — `RunTracer` writes one JSONL event
   per `run_start` / `llm_call` / `llm_response` / `tool_call` /
   `tool_result` / `run_end`, and the CLI prints a summary (tokens, calls,
   turns, latency).

**File-by-file role (verified from each file's own module docstring):**

| File | Actual role (from the code) |
|---|---|
| `forge/agent.py` | Implements `AgentRuntime.run()` — the loop: build context → LLM call → validate/execute any tool calls → loop → stop on final answer or a hard limit. Turns every failure mode into a recorded event, never a crash. |
| `forge/cli.py` | The `forge` console-script entry point (`argparse`-based). Defines all six subcommands and their options; the whole options reference in Section 5 comes directly from this file's docstring and parser. |
| `forge/llm.py` | Defines the provider-agnostic vocabulary — `Message`, `ToolCall`, `LLMResponse`, `LLMError`, the `LLMProvider` ABC, and `get_provider()`. Nothing outside `forge/providers/` touches a provider SDK. |
| `forge/tools.py` | `Tool` ABC, `ToolResult`, `ToolRegistry` (name → tool lookup, `get_schemas(subset)`), and the `ToolExposureStrategy` seam (`FixedToolExposure`, `AdaptiveToolExposure`). |
| `forge/builtin_tools.py` | The five concrete tools and `build_default_registry()`. Every tool validates its own inputs, never raises, and routes through `forge.safety`. |
| `forge/context.py` | `ConversationContext` (message history container) and the `ContextStrategy` seam (`RawContextStrategy`, `ManagedContextStrategy`) plus `ContextReport` measurement. |
| `forge/config.py` | Loads and validates all settings from environment variables (`.env` via `python-dotenv`). No secrets hard-coded. |
| `forge/safety.py` | `assert_within_workspace()`, `assert_safe_write()`, `assert_safe_command()` — the workspace-boundary, overwrite-guard, and command-blocklist checks every tool calls before touching disk/shell. |
| `forge/observability.py` | `RunTracer`, `RunEvent`, `RunSummary` — records typed events per run and flushes them to a JSONL trace file; never fabricates a metric (`None` ≠ `0`). |
| Provider files (`forge/providers/*.py`) | One adapter per LLM backend (Gemini, Groq, Cerebras) plus `FallbackProvider`, which orders several adapters (e.g. Gemini → Groq → Cerebras) behind the same `LLMProvider` interface so the agent loop never knows a fallback happened. |
| Evaluation files (`forge/evaluation/*.py`) | The measurement layer above the agent loop: `EvalTask`/`suite.py` (task suite loading), `ExperimentConfig`/`runner.py` (one controlled run), `matrix.py` (the formal four-arm 2×2), `analysis.py` (Step 8 statistics). |

### 5.4 `forge run`

Purpose: execute the agent once on a single task and print a summary. This
is the command used for the live demo in Section 6.

```text
usage: forge run [-h] --task TASK [--workspace WORKSPACE] [--model MODEL]
                 [--max-turns MAX_TURNS] [--max-tool-calls MAX_TOOL_CALLS]
                 [--temperature TEMPERATURE] [--no-trace] [--json] [--quiet]

options:
  -h, --help            show this help message and exit
  --task TASK           the coding task, in natural language
  --workspace WORKSPACE
                        workspace root (default: cwd)
  --model MODEL         override the model name
  --max-turns MAX_TURNS
                        max LLM turns
  --max-tool-calls MAX_TOOL_CALLS
                        max tool calls
  --temperature TEMPERATURE
                        sampling temperature
  --no-trace            do not write a JSONL trace
  --json                print the run summary as JSON
  --quiet               only print the final answer
```

Plain-language meaning of each option:

| Option | Meaning |
|---|---|
| `--task` | The coding instruction you want the agent to carry out (required). |
| `--workspace` | Which folder the agent is allowed to read/write in. Defaults to the current directory — **always point this at a disposable folder, not the FORGE source tree.** |
| `--model` | Use a different model name than the one configured in `.env`. |
| `--max-turns` | Hard ceiling on how many LLM ↔ tool round trips the run can take before it is stopped. |
| `--max-tool-calls` | Hard ceiling on the total number of tool calls in the run. |
| `--temperature` | Sampling randomness passed to the model (0.0 = deterministic). |
| `--no-trace` | Skip writing the JSONL trace file for this run. |
| `--json` | Print the run summary as machine-readable JSON instead of plain text. |
| `--quiet` | Print only the model's final answer, nothing else. |

### 5.5 `forge evaluate`

```text
usage: forge evaluate [-h] (--task TASK | --task-file TASK_FILE |
                      --suite-task-id SUITE_TASK_ID) [--suite-dir SUITE_DIR]
                      [--task-id TASK_ID] [--tool-strategy TOOL_STRATEGY]
                      [--context-strategy CONTEXT_STRATEGY]
                      [--workspace WORKSPACE] [--model MODEL]
                      [--max-turns MAX_TURNS]
                      [--max-tool-calls MAX_TOOL_CALLS]
                      [--temperature TEMPERATURE]
                      [--results-file RESULTS_FILE] [--label LABEL]
                      [--no-trace] [--json]
```

- **Purpose:** run one task under one explicit `(tool_strategy,
  context_strategy)` configuration and append a structured `EvalResult` row
  (JSON) to a results file — the single-cell building block that
  `forge experiment` / `forge demo` run automatically, many times over.
- **Key options:** the task source is one of `--task` (inline prompt),
  `--task-file`, or `--suite-task-id` (from the baseline suite);
  `--tool-strategy` (`fixed`|`adaptive`) and `--context-strategy`
  (`raw`|`managed`) select the configuration; `--results-file` controls
  where the JSONL row is appended (default `runs/eval_results.jsonl`).
- **What it records:** per the CLI's own printed fields — `task_id, run_id,
  status, success, tool_strategy, context_strategy, llm_calls, tool_calls,
  input_tokens, output_tokens, total_tokens, reasoning_tokens,
  cached_input_tokens, latency_ms, cost_usd, cost_available,
  context_messages, context_char_count, context_items_dropped,
  context_items_compressed, context_chars_saved, checks_run, checks_passed,
  duration_s, trace_path`.
- **Should it be run during the professor demo?** It is safe (one real API
  call) but **not necessary** — this repository already contains recorded
  `forge experiment` and `forge demo` output (`runs/experiments/`,
  `runs/step10_demo/`) that exercises the exact same underlying
  `EvaluationRunner` path. No `runs/eval_results.jsonl` (the default
  standalone-evaluate output) currently exists in this repository —
  **Needs verification** whether the team wants to generate one before the
  demo, or rely on the existing experiment/demo artifacts instead.

### 5.6 `forge experiment`

```text
usage: forge experiment [-h] [--suite-dir SUITE_DIR] [--task-id TASK_IDS]
                        [--arm {fixed_raw,fixed_managed,adaptive_raw,adaptive_managed}]
                        [--output-dir OUTPUT_DIR]
                        [--experiment-id EXPERIMENT_ID] [--label LABEL]
                        [--model MODEL] [--max-turns MAX_TURNS]
                        [--max-tool-calls MAX_TOOL_CALLS]
                        [--temperature TEMPERATURE] [--no-trace] [--json]
```

- **Purpose:** the formal, research-grade 2×2 controlled experiment (Step
  7). Runs every selected task under all four arms
  (`fixed_raw`, `fixed_managed`, `adaptive_raw`, `adaptive_managed`), each
  in its own isolated workspace, and writes one reloadable
  `results.jsonl` + `metadata.json` per experiment run.
- **The four arms:** exactly the `--arm` choices shown above — Fixed+Raw,
  Fixed+Managed, Adaptive+Raw, Adaptive+Managed.
- **Is it safe to run during the demo?** The CLI's own docstring gives an
  explicit warning: *"with no provider override this calls the real
  configured LLM provider (Gemini by default) once per task-arm
  execution — a full 4-arm run against the baseline suite is one real API
  call sequence per cell and will consume real quota."* It is **not
  dangerous** (it never touches files outside its own output directory),
  but it does spend real API quota and time.
- **Is it time-consuming?** Yes, relative to a single `forge run` — a full
  suite × four arms means many sequential agent runs. This repository
  already has multiple completed `forge experiment` runs recorded under
  `runs/experiments/` (e.g. `step9_real_four_arm_baseline`,
  `step9_research_multitask`) — these can be shown to the professor
  directly instead of re-running the experiment live. **Do not run this
  command live unless explicitly approved.**

```text
usage: forge demo [-h] [--suite-dir SUITE_DIR] [--task-id TASK_ID]
```

  provider, or evaluation logic beyond `forge experiment`.

  recorded under `runs/step10_demo/` (each a full 4-arm run of
  `create-string-utils`), which can be shown directly.

### 5.8 `forge analyze`

```text
usage: forge analyze [-h] --results RESULTS [--metadata METADATA]
                     [--output OUTPUT]
                     [--arm {fixed_raw,fixed_managed,adaptive_raw,adaptive_managed}]
                     [--task-id TASK_IDS] [--overwrite] [--json]
```

- **Purpose:** Step 8 statistical analysis. Reads an existing
  `results.jsonl` (and its `metadata.json`, if present) and writes a
  reproducible, machine-readable comparison across arms — descriptive
  statistics, paired task comparisons, and a stdlib-only Wilcoxon
  signed-rank statistic. It **deliberately never computes or prints a
  p-value, confidence interval, or "significant" label** (documented
  design decision, `docs/step-08-statistical-analysis.md` §7).
- **Safety:** read-only. Per the CLI docstring: *"reads only; never calls a
  provider or the network, and never modifies the source results
  JSONL."* This is the **safest command to demo live**, e.g. against an
  already-recorded results file such as
  `runs/experiments/step9_real_four_arm_baseline/results.jsonl`.

- `--json` — prints the run summary (status, tokens, calls, latency, trace

## FORGE Efficiency: Token Usage, Calls, and Execution Overhead

This section treats the FORGE numbers as one **observed single-run
example**, not a universal conclusion, and clearly separates what is
measured directly from what is inferred.

**1–7. What FORGE measures directly (all sourced from the verified trace above):**

1. **Input tokens** — 5,855 for the hello.py run.
2. **Output tokens** — 127.
3. **Total tokens** — 6,529.
4. **LLM calls** — 5 (one per agent turn).
5. **Tool calls** — 4 (`list_directory`, `read_file`, `run_shell` ×2).
6. **Execution latency** — 18,990.8 ms of cumulative LLM latency for the run.
7. **Context size** — tracked per turn as `context_messages` /
   `context_char_count`; the trace shows context growing from 1,204 to
   1,487 characters over the five turns of this run.

**8. Repeated context overhead** — because `RawContextStrategy` (the
strategy used in this run: `context_strategy: "raw"` per the trace's
`run_start` event) resends the full history every turn, each of the five
LLM calls in this run re-sent all prior messages, which is why input tokens
grew turn over turn (836 → 1,130 → 1,194 → 1,314 → 1,381, per the trace's
`llm_response` events). `ManagedContextStrategy` exists specifically to
reduce this (Section 10).

**9. Cache usage** — the trace records `cached_input_tokens: null` for
every call in this run, meaning **no cached-token usage was reported** by
the provider for this run. **Needs verification** whether any other
recorded run in this repository shows non-null cached tokens.

**10. Why lower token usage can matter:**

- **API cost** — most providers bill per input/output token; fewer tokens
  per run means lower direct cost.
- **Response latency** — larger context generally means more tokens for the
  model to process before it can respond.
- **Resource consumption** — fewer tokens and calls mean less compute spent
  per completed task.
- **Scalability** — a harness that uses fewer tokens per task can serve more
  tasks/users for the same budget.
- **Environmental impact proxies** — token/compute usage is a commonly used
  proxy for the energy cost of running a model; it is not an exact
  measurement, only a proxy.

### Research interpretation

FORGE's harness layer is explicitly designed to measure — and, through its
Adaptive/Managed strategies, potentially reduce — input-token overhead,
output-token usage, repeated context transmission, unnecessary LLM calls,
unnecessary tool calls, execution latency, and API cost. This connects
directly to the research design in Section 10:

- **Fixed vs. Adaptive Tool Exposure** — does exposing fewer, task-relevant
  tools reduce token/call overhead?
- **Raw vs. Managed Context** — does pruning/compressing history reduce
  repeated-context token overhead?
- **Four configurations** — Fixed+Raw, Fixed+Managed, Adaptive+Raw,
  Adaptive+Managed — let both variables be tested independently and in
  combination.

The purpose of the 2×2 experiment is to determine whether Adaptive tool
exposure and Managed context can reduce resource usage **while preserving
task correctness** — not to declare either configuration a winner without
running and analyzing the experiment (`forge analyze`) on real results.

## Section 10 — Research Design

Verified against `docs/architecture.md` §"Research Arms" and
`forge/evaluation/matrix.py` (the four arm ids used by the CLI's `--arm`
option).

| Tool Exposure | Context | Configuration |
|---|---|---|
| Fixed | Raw | Fixed + Raw (`fixed_raw`) |
| Fixed | Managed | Fixed + Managed (`fixed_managed`) |
| Adaptive | Raw | Adaptive + Raw (`adaptive_raw`) |
| Adaptive | Managed | Adaptive + Managed (`adaptive_managed`) |

**Fixed tool exposure** (`FixedToolExposure`) — all registered tools are
always exposed to the LLM on every turn. This is the Step 2 baseline.

**Adaptive tool exposure** (`AdaptiveToolExposure`, Step 5) — only the
tools plausibly relevant to the current task are exposed, chosen by a
**deterministic keyword classification** (explicitly not ML-based — chosen
for determinism and explainability per the architecture decision log).

**Raw context** (`RawContextStrategy`) — the full, unmodified conversation
history is sent to the LLM on every turn. This is the Step 2 baseline.

**Managed context** (`ManagedContextStrategy`, Step 6) — a **deterministic,
rule-based** pruning/compression policy: it always keeps the task, a recent
window of turns, and any turn containing a failed tool result; it drops or
compresses older, redundant, successful tool output; and it enforces a
hard message/character budget. No summarisation model or extra LLM call is
used.

**Why these configurations are compared:** Tool exposure and context
management are two independent seams in the same agent loop
(`ToolExposureStrategy` and `ContextStrategy`), so their four combinations
can each be run under otherwise identical conditions (same model, same
task, same limits) — isolating the effect of each variable and their
interaction.

**What metrics are collected:** the same per-run metrics as Section 8
(tokens, LLM calls, tool calls, latency, context size), plus task
success/failure (`checks_passed`) and, for Managed-context runs,
`context_items_dropped` / `context_items_compressed` / `context_chars_saved`.

**On declaring a winner:** this guide does **not** claim any configuration
is better than another. `forge analyze` (Section 5.8) is the tool designed
to make that comparison from real results, and per
`docs/step-08-statistical-analysis.md` it deliberately stops at descriptive
statistics — it does not label any difference as "significant."
Recorded results from real runs already exist under `runs/experiments/`
(e.g. `step9_real_four_arm_baseline/analysis.json`) — **Needs
verification** whether the team wants to present those specific numbers to
the professor; they were not re-derived for this guide to avoid mixing the
simple demo with formal research results, per the constraints of this
document.

## Section 14 — Professor Questions and Answers

1. **What is the main purpose of FORGE?**
   To measure how a coding agent's harness strategy — tool exposure and
   context management — affects task success, token usage, cost, and
   latency, under controlled, repeatable conditions.

2. **How is FORGE different from a normal chatbot?**
   It executes real tools against a real filesystem inside a bounded
   workspace, enforces hard turn/tool-call limits, and records a complete
   structured trace and metrics for every run — a chatbot does none of
   this.

3. **Why is it called provider-agnostic?**
   The agent loop only depends on the `LLMProvider` abstract interface
   (`forge/llm.py`); it never imports a provider SDK directly. Concrete
   adapters (Gemini, Groq, Cerebras) live only in `forge/providers/` and
   can be swapped without touching the agent, tools, or evaluation code.

4. **Which model is currently being used?**
   `gemini-3.6-flash`, via the Gemini provider — the default and the one
   actually exercised in the recorded runs in this repository.

5. **What are tools in your system?**
   Discrete capabilities the LLM can invoke during a run:
   `read_file`, `write_file`, `edit_file`, `list_directory`, and
   `run_shell` — each validated and routed through the safety layer.

6. **Where are generated files saved?**
   Inside whatever `--workspace` path was given to the run (e.g.
   `runs/manual_test/` for the Section 6 demo) — never inside the FORGE
   source tree.

7. **What is a JSONL trace?**
   A file with one JSON object per line, one line per event
   (`run_start`, `llm_call`, `llm_response`, `tool_call`, `tool_result`,
   `run_end`), giving a complete, ordered, machine-readable record of one
   agent run.

8. **What is the difference between input and output tokens?**
   Input tokens are everything sent to the model (system prompt, task,
   conversation history, tool schemas); output tokens are what the model
   generates in response.

9. **Why are tool calls and LLM calls measured separately?**
   They represent different costs: an LLM call costs tokens/latency at the
   model; a tool call costs local execution time and can fail
   independently (e.g. a shell command returning a non-zero exit code, as
   actually happened mid-run in the trace used in this guide).

10. **What is adaptive tool exposure?**
    A strategy (`AdaptiveToolExposure`, Step 5) that exposes only the tools
    a task plausibly needs, chosen by a deterministic keyword classifier,
    instead of always exposing every tool.

11. **What is managed context?**
    A strategy (`ManagedContextStrategy`, Step 6) that deterministically
    prunes and compresses older, redundant conversation history while
    always preserving the task, a recent window, and any failed-tool-result
    turn — reducing repeated-context token overhead.

12. **Why are there four experiment configurations?**
    Tool exposure and context management are independent variables; a 2×2
    design (Fixed/Adaptive × Raw/Managed) lets each variable's effect, and
    their interaction, be measured separately rather than confounded.

13. **Why do you need isolated workspaces?**
    So that one run's file changes can never contaminate another run, the
    FORGE source tree, or a parallel run in the same experiment — required
    for a fair, repeatable comparison.

14. **How do you verify task correctness?**
    Each baseline task defines one or more `checks` (per `forge tasks`'
    "checks" column); `EvaluationRunner` runs these checks against the
    produced workspace and records `checks_passed`/`success`.

15. **What is already completed?**
    The agent loop, all five built-in tools, the safety layer, three LLM
    provider adapters plus fallback, observability/JSONL tracing, the full
    CLI (all six commands), the 10-task baseline suite, the Fixed/Adaptive
    and Raw/Managed strategies, the 2×2 `MatrixRunner`, Step 8 statistical
    analysis, and 507 passing automated tests (verified in this session).

16. **What is still future work?**
    Per `README.md`'s own "Intentionally not implemented" list (noting some
    entries are now outdated — see Section 4) and this guide's findings: a
    larger-scale, statistically powerful 2×2 run and its analysis; a fully
    controlled (not just observed) comparison against external agents like
    Antigravity — the `runs/benchmarks/antigravity_vs_forge/` scaffold
    exists but its own README currently states no real comparison run has
    been executed there; a WhatsApp/Telegram interface; and refreshing
    `README.md` to reflect the current implementation state.
